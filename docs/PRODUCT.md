# ArchiEvidence 产品方案与效果验收

本文基于现有学习原型整理，采用 AI 辅助编写。面向个人笔记检索的用户需求属于待验证假设；当前没有真实用户访谈或使用增长数据。

## 用户场景与产品目标

假设用户积累了多篇 Markdown 或 TXT 学习笔记，需要找到与问题有关的内容，并确认原文出处。目标是缩短查找路径，同时让检索结果可追溯。

现有样例包括 AI 工程和建筑学习材料，均为教学笔记。产品不提供建筑规范合规判断。实现入口见 `archi_agent/agent.py` 和 README。

## 用户流程与能力边界

离线流程：导入笔记 → 分块并保存来源行号 → 建立 SQLite FTS5 索引 → 提问 → 查看摘录、文件、行号与片段编号。

在线工具调用流程：模型提出检索或算式计算请求 → 程序校验工具及参数 → 执行后回传结果 → 模型继续处理 → 核对引用编号。在线路径已实现并通过模拟消息测试，尚未进行真实服务商端到端验证。网页当前只使用离线检索。

## 功能取舍

| 优先级 | 方案 | 理由与当前状态 |
| --- | --- | --- |
| P0 | 离线笔记检索与原文来源 | 已实现，便于无密钥运行和核对依据 |
| P0 | 无结果提示、输入校验、索引替换 | 已实现，让用户知道何时需要补充资料 |
| P1 | 在线工具调用、参数校验与轮次限制 | 代码与模拟测试已实现；真实模型联调待完成 |
| P1 | MCP 工具接口 | 已通过官方 SDK 客户端测试；未完成 Codex 或 Claude Code Host 联调 |
| 后续 | 更好的无答案判断、向量检索或重排对照 | 尚未实现；需先用独立题集比较收益 |

采用 BM25 作为当前检索方案，可以直接检查检索词与来源、离线复现。当前不包含 embedding、向量数据库或模型微调。是否更换方案，应由目标资料和实际问题上的对照评测决定。

## 交互与异常验收

- 有结果：展示摘录和出处；用户应能定位到原文件和行号。
- 无结果：明确提示知识库不足，不用空白页面代替反馈。但有结果也可能缺少真正相关的证据。
- 重新索引：新知识库原子替换旧内容，删除的文档不应继续被检索。
- 非法工具或参数：拒绝执行并返回错误；每轮最多四次工具调用，默认最多五轮。
- 模型引用不存在的片段编号，或没有可核对引用：停止输出结论。当前只验证引用编号是否存在，不能据此保证回答与来源的语义一致。

## 已有验证与发现

25 项自动化测试通过，覆盖检索来源、索引更新、工具边界、API 和 MCP 等。自建评测集包含 12 道有答案题与 3 道无答案题，报告见 `reports/evaluation.json`。

在这套演示题中，12 道有答案题的相关来源均排在首位；3 道无答案题中有 1 道发生误召回。样例笔记与题目来自同一项目，没有独立测试集；这些结果不能代表真实用户场景或大模型通用准确率。

误召回提示：仅凭“查到了内容”不足以判断“内容能回答问题”。后续可先增加独立问题、保存人工相关性标注，再评估阈值、检索方式与展示文案。

## 待验证的产品指标

以下指标仅完成定义，尚未采集真实用户数据。

- 找到依据的任务完成率：能定位并解释相关原文的任务数 / 全部查找任务数。
- 来源定位耗时：从提问到在原文中找到依据的时间。
- 无答案误召回比例：人工确认无依据却展示为候选内容的题数 / 无依据题总数。
- 在线回答的语义支持度：由人工逐条检查回答是否由引用支撑；与引用编号存在性分别记录。

首轮试用计划使用不含个人资料的学习笔记，让参与者先手工查找，再使用工具完成等价任务，分别记录耗时、失败点与来源核对情况。尚未开展试用，未设置虚构的提升比例。
